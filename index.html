Path of Exile on Linux: the hideout that took forever after every restart

The game was reloading every shader it owned each time it started. Not disk, not RAM, not permissions. The NVIDIA driver was deleting its own cache at launch, and Steam had quietly stopped protecting it.

The fix

git clone https://github.com/tinycrops/poe-linux-shader-cache-fix
cd poe-linux-shader-cache-fix
./check.sh   # read-only: is the cache being wiped?
./fix.sh     # raise the NVIDIA shader cache limit to 20 GiB, disable cleanup, session-wide

Under the hood it is two environment variables, set for the whole desktop session rather than as a per-game launch option:

__GL_SHADER_DISK_CACHE_SIZE=21474836480
__GL_SHADER_DISK_CACHE_SKIP_CLEANUP=1

No sudo. Quit and restart Steam, then log out and in once. The first launch after that is the last cold compile.

The symptom

Path of Exile 2 on a GTX 1060 6 GB, Ubuntu 24.04, Proton Experimental, the game's native Vulkan renderer. Play ran fine. But every restart of the game sat on the hideout loading screen for minutes, and the request that started this was simply: "every time I restart my Path of Exile 2 game the hideout takes forever to load. please fix this."

What the logs said, in order

  1. The obvious suspect was a red herring. The game's own log, logs/Client.txt, prints this on every launch: 
    [CRIT Client 308] Failed to open LMDB environment at C:\users\steamuser\AppData\Local\Path of Exile 2\Pipelines. Error: Access denied.
[CRIT Client 308] Failed to open LMDB environment at C:\users\steamuser\AppData\Local\Path of Exile 2\Shaders. Error: Access denied.
    That is the game's persistent pipeline cache failing to open. It reads like a permissions problem, and the first instinct (mine and the user's) was to fix permissions. But the folders are owned by the user, mode 775, files 664, the data.mdb inside is a fresh 8 KB every launch, and the error appears in 30 of 30 launches since install, and 324 times in Path of Exile 1's log too. It is a failure inside Wine's Windows API layer, not the filesystem. Real, unfixed, and not the cause of the slow load.
  2. The driver's cache was being written to the wrong place. Steam normally hands NVIDIA games a managed cache directory under steamapps/shadercache/<appid>/nvidiav1. That directory's files had last been written on Sep 4 at 18:50, although the game had run twenty times since. The running game's open file descriptors showed where the driver was actually writing: ~/.cache/nvidia/GLCache/…/92f74448a56b9fe8.bin, the driver's default location.
  3. Steam's shader log dated the change exactly. logs/shader_log.txt contains a Setting MESA_GLSL_CACHE_DIR=…/shadercache/2694490 line for every launch where Steam applied its managed cache. Five launches had it, the last at Sep 4 18:41. Every launch after Steam restarted at 19:38 that evening lacked it, for both games. The Steam client version changed at that restart (1785799196 → 1788400362). Steam still downloads and processes shader buckets in the background; it just no longer applies them at launch. Cause not established beyond that correlation.
  4. The default cache has a 1 GiB limit, and the driver wipes it. From the NVIDIA README, chapter 11K: if the cache is over the size limit when an application starts, the driver deletes it. The limit has been 1 GiB since driver 460 (128 MB before that). The README also warns that any app started without a raised limit reverts to the default and can wipe the cache, which is why a per-game launch option is not enough.
  5. File birth times proved the wipe. stat -c %w on the driver's cache directory: the whole per-driver folder and every file in it had been created at 04:15:37 on Sep 11, the exact second of the previous game launch. The file the running game was writing had reached 200 MB thirteen minutes in and 680 MB an hour later.
  6. Path of Exile 1 shows how far over the limit these games go. Its Steam-managed NVIDIA cache, from before Sep 4, is a single 5.2 GB file. Steam's managed path carries no limit; the driver's default path throws all of that away the moment a session pushes it past 1 GiB. One evening of mapping is enough, so nearly every launch started cold, and the hideout, being the first area, paid for recompiling everything.

Everything is idempotent and needs no sudo. SHADER_CACHE_SIZE=<bytes> ./fix.sh picks a different limit; ./fix.sh --dry-run only prints.

Verifying it worked

After a long session and a restart, the driver's cache files should keep their creation date across launches:

stat -c '%w  %10s  %n' ~/.cache/nvidia/GLCache/*/*/*.bin

If a file's creation time equals a launch time, the cache was wiped at that launch. check.sh prints the same view, plus whether the variables are set and whether Steam is applying its own cache.

Update, day two: a second limit at 2 GiB per cache file

With the wipe gone, the cache grew to 2.1 GB over a day of play and every restart was fast. Then one restart was cold again, with nothing wiped. The running game had a different cache file open: a 32-byte stub the driver had created the day before, now filling up fast, while the 2.1 GB file sat untouched with nobody holding it. That file had stopped growing at 2,155,662,949 bytes, a few MB past 231, in the last minute of the previous session.

The decisive test was to parse both tables of contents (32-byte header, then 32-byte entries of key, offset, size) and compare keys: 98.6% of the shaders the game was compiling into the new file were already in the abandoned one. The driver was not reading it. So there is an undocumented per-file limit at 2 GiB: once a cache file crosses it, the driver starts a fresh file and ignores the old data, which from the game's point of view is the same as a wipe. overlap.py in the repo runs that comparison.

What this means in practice: the size variable stops the driver deleting the cache, but a game that compiles this many shader variants will still go cold roughly once per 2 GiB of new pipelines, about a day of mapping here. The way out is Steam's own shader-cache management, which merges and deduplicates driver caches (Path of Exile 1's managed cache had reached 5.2 GB in one file and kept working) and which on this machine stopped being applied after the Sep 4 client update. Whether that is a client change or a toggle (Steam → Settings → Downloads → Shader Pre-Caching) is the open question.

Still open

  • The LMDB "Access denied" failure means the game's own pipeline cache never persists under Proton. Same on Proton 10 (PoE 1) and Proton Experimental (PoE 2). With the driver cache intact it stops mattering much, but a native fix would be better. No known workaround found.
  • Why Steam stopped applying its managed cache after the Sep 4 client update. If it resumes, nothing here conflicts: Steam's path sets its own variables per launch.
  • The client logs [SteamdeckSettingsInit] running on steamdeck: 1 on a desktop and re-applies Steam Deck display defaults each launch. Unrelated, noted.
How this was diagnosed (the making-of)

All of it was done while the game was running, read-only, without touching the process: Client.txt and LatestClient.txt for the game's own view; /proc/<pid>/environ to see that no __GL_SHADER_DISK_CACHE_PATH had been passed; /proc/<pid>/fd to see which cache file the driver actually had open; stat -c %w for birth times, which ext4 keeps and which turned a hypothesis into a timestamp; Steam's logs/shader_log.txt and console_log.txt for when the managed cache was and was not applied; and the driver's own README on disk for the rule that explained the wipe. The one tempting shortcut, "rewrite the permissions", was checked and rejected on the numbers before anything was changed.

Tested on

Ubuntu 24.04, GNOME on X11, NVIDIA 580.173.02, GTX 1060 6 GB, Steam 1788652215, Path of Exile (Proton 10) and Path of Exile 2 (Proton Experimental), both on the native Vulkan renderer.
